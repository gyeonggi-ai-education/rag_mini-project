## 2. 작업 분담

| 담당 | 주 책임 | 병렬 작업 | 인수 조건 |
|---|---|---|---|
| A: 본인, 데이터·청킹 | Docling 로딩, 법률 구조 검증, 청킹, 메타데이터, 임베딩·Qdrant 적재 | 실제 조문 소량 샘플 공유, 조문 정답 검토 | 원문 대비 누락·경계 확인, 샘플 및 전체 데이터가 동일 형식, 적재 재실행 시 중복 방지 |
| B: Rerank | 공통 Dense 검색과 Rerank 구현 | FastAPI, Context 구성, 답변·출처 생성 및 통합 | 기준선과 Rerank를 같은 인터페이스로 실행, /ask 동작, 반환 출처가 실제 사용 근거와 일치 |

B의 통합 부담이 커지면 A가 전체 적재 완료 후 노트북 정리와 문서 QA를 맡고, C가 실험 자동화를 맡는다. 최종 보고서는 각자 담당 단계의 실패 사례와 수치를 작성하고 함께 편집한다. 3시간 일정에서는 B의 API·Dense 연결을 우선하고 Rerank 튜닝 횟수를 제한한다.

검색 담당자 둘은 별도의 API 서버를 만들지 않는다. 검색 모듈을 각각 구현하고 공통 API에 연결한다. 전체 인덱스 적재는 A가 담당하고 B·C는 읽기 중심으로 사용한다.

## 3. 청킹 완료를 기다리지 않는 개발 방식

1. 세 사람이 짧은 킥오프에서 Chunk·검색 결과 형식, 임베딩 설정, Qdrant 컬렉션 규칙을 먼저 합의한다.
2. A가 실제 PDF의 대표 조문을 수작업으로 확인해 소량의 sample_chunks.jsonl을 먼저 제공한다. 자동 청킹 완성은 기다리지 않는다.
3. B는 샘플을 이용해 Dense → 답변 → /ask 흐름을 연결하고, 같은 후보 목록에 Rerank를 적용한다.
4. C는 같은 샘플과 Dense 인터페이스를 사용해 Multi Query 및 평가 도구를 만든다.
5. A가 검증한 전체 Chunk를 전달하면 동일 형식으로 컬렉션만 교체하고 회귀 평가한다.

실제 샘플 전달 전에는 가짜 데이터를 인터페이스 연결 확인에만 사용한다. 샘플이나 가짜 데이터 결과를 전체 문서 검색 성능으로 보고하지 않는다.

## 4. 먼저 고정할 공통 계약

### Chunk

첫 10분에 필수 필드를 chunk_id, document_id, document_version, article, content로 고정한다. law_name, article_title, paragraph, chapter, section, page_start, page_end, is_supplementary는 선택 필드로 두고 추출 가능한 값만 채운다. 본문과 부칙을 섞어 처리한다면 is_supplementary 또는 동등한 구별 필드는 반드시 채운다. 메타데이터 확장 때문에 샘플 전달을 늦추지 않는다.

- document_version: 본문에서 확인한 법률 버전 표기. 확인 전에는 미확정으로 기록한다.
- article: 제2조와 같은 원문 조문 표기. 부칙은 본문과 구별할 필드를 추가한다.
- paragraph, chapter, section: 해당 구조가 없으면 null로 둔다. 값을 추측하지 않는다.
- page_start, page_end: PDF 물리 페이지 기준 1부터 시작하도록 합의한다.
- content: 출처로 제시할 수 있는 실제 법률 본문. 임베딩용 제목·경로 결합 텍스트가 필요하면 별도로 만든다.
- chunk_id: 문서 버전·조문 경로·분할 순서로 재현 가능하게 생성한다. 구조나 청킹 규칙을 바꾸면 데이터 버전을 바꾼다.

Qdrant point ID와 chunk_id의 매핑은 A가 관리한다. 컬렉션에는 임베딩 모델·차원·데이터 버전을 기록하고, 문서와 질문에 동일한 임베딩 설정을 사용한다.

### 모델 호출 설정

- 환경변수: MONOROUTER_API_KEY, MONOROUTER_BASE_URL. 실제 값은 환경에서 주입하고 저장소에 기록하지 않는다.
- 추가로 합의할 설정: 답변·질의 확장용 모델 ID, 임베딩 모델 ID, Rerank 방식 및 모델 ID. 환경변수 이름만으로 지원 기능을 가정하지 않는다.
- B가 공통 모델 호출 어댑터를 소유하고 C는 질의 확장에 이를 사용한다. A와 B는 동일 임베딩 호출 함수를 공유한다. C가 공통 파일 수정 완료를 기다리지 않도록 첫 10분에 함수 입력·출력과 실패 동작을 합의한다.
- 첫 15분 안에 채팅 호출 및 임베딩 호출을 각각 소량으로 확인한다. Rerank 전용 API 지원도 확인한다. 채팅 지원 확인만으로 임베딩·Rerank 지원이 확인된 것으로 간주하지 않는다.
- 전용 Rerank API가 없다면, 사용 가능한 채팅 모델로 제한된 후보의 관련성을 평가해 재정렬하는 방식을 대안으로 논의한다. 이를 사용할 때 보고서에 LLM 기반 재정렬임을 명시하고 지연·비용을 기록한다. 임베딩이 지원되지 않으면 이용 가능한 별도 API 또는 사전 준비된 로컬 모델을 확정해야 한다.

### 검색 인터페이스

공통 논리 인터페이스: `retrieve(question, candidate_k) -> list[RetrievedChunk]`

검색 결과는 Chunk 필드에 retrieval_score, rerank_score, rank를 더한다. 서로 다른 단계의 점수는 구분하며, 점수 의미가 다른 결과를 단순 합산하지 않는다.

역할별 연결 지점:

- B: dense_retrieve(question, candidate_k)와 rerank(question, candidates, final_k)
- C: expand_queries(question)와 multi_query_retrieve(question, candidate_k)
- 통합: 선택한 검색 모드의 후보 목록 → 선택적 Rerank → 최종 Context → 답변

초기에는 API·평가 도구가 내부 설정으로 네 검색 모드를 바꿀 수 있게 한다. 공개 /ask 요청은 사용자가 제시한 question 형식을 유지한다.

### API

입력: `{"question": "고영향 인공지능이란 무엇인가요?"}`

출력: `{"answer": "검색 근거에 기반한 설명", "sources": [{"article": "제○조", "content": "실제로 사용한 법률 내용"}]}`

내부에서는 출처 ID·항·페이지를 보존한다. 답변의 각 주요 주장과 출처를 연결하고, 출처 목록은 검색 결과 전체가 아니라 답변에 사용한 근거로 구성한다. 근거가 부족하면 문서에서 확인하기 어렵다고 답하도록 한다. 빈 질문, 검색 결과 없음, 외부 모델 실패 처리도 MVP에 포함한다.

## 5. 청킹 선택 기준

시작 가설은 조문 단위 청킹이다. 긴 조문은 항 단위로 나누되 조문 번호·제목을 유지한다. 여러 항의 관계가 필요한 질문은 검색 후 동일 조문 보강을 검토한다.

데이터 담당자는 다음을 원문과 대조한다.

- 장·절 제목이 본문으로 섞이거나 조문 경계가 잘리는지
- 항·호·목 번호, 정의 목록, 단서 문구가 유지되는지
- 머리말·쪽 번호가 검색 텍스트에 반복되는지
- 본문과 부칙의 동일 조문 번호가 혼동되는지
- PDF 추출 누락, 줄바꿈, 표가 의미를 훼손하는지

청킹 크기와 중첩은 미리 성능이 좋다고 단정하지 않는다. 조문 보존, 과도한 길이, 검색 실패 사례를 보고 변경하고 데이터 버전별 결과를 남긴다.

## 6. 검색 비교 실험

Rerank는 후보 순서 개선, Multi Query는 질문 표현에 따른 검색 누락 개선이라는 가설로 시작한다. 효과는 평가 결과로 판단한다.

| 모드 | 흐름 | 확인하려는 효과 |
|---|---|---|
| baseline | 원질문 → Dense → 최종 K | 비교 기준 |
| rerank | 원질문 → Dense 후보 → Rerank → 최종 K | 후보에 존재하는 근거의 순위 개선 |
| multi_query | 원질문 + 확장 질의 → Dense → 병합 → 최종 K | 표현 차이로 놓친 근거 회수 |
| combined | Multi Query → 병합 후보 → Rerank → 최종 K | 두 개선의 결합 효과 |

Multi Query는 원질문을 반드시 포함하고 확장 질의 수를 제한한다. 검색 결과는 chunk_id로 중복 제거한다. 병합은 RRF 같은 순위 기반 방법을 첫 실험안으로 두고 평가한다. BM25·Hybrid를 이번 MVP의 추가 목표로 넣지는 않는다.

초기 실험값 제안: 후보 20개, 최종 K=5, 확장 질의 최대 3개. 이는 확정값이 아니며 지연·비용과 검색 결과를 보고 조정한다. Multi Query의 전체 후보 예산도 명시하고, 결합 실험에서는 Rerank 입력 후보 수를 제한한다.

비교할 때 문서·청킹·임베딩·평가셋·최종 K·답변 모델과 프롬프트를 고정한다. 후보 예산과 모델 호출 수는 함께 기록해 개선이 추가 연산에서 나온 것인지 판단한다. Rerank 전 후보 Recall도 확인해 후보 누락과 순위 문제를 구별한다.

## 7. 평가와 보고서

Golden Set은 팀이 원문을 확인해 만든다. 3시간 기준으로 답변 가능한 8문항과 답변 불가 2문항, 총 10문항부터 확보한다. 4시간을 확보하면 총 15문항 정도로 확장한다. 정의, 적용 범위, 의무·예외, 여러 조문이 필요한 질문, 일상 표현을 포함한다. 소규모 탐색 결과라는 한계를 보고서에 명시한다.

각 문항에 질문 ID, 질문 유형, 정답 조문·항, 필수 답변 요소, 답변 가능 여부를 기록한다. 조문 기반 정답을 먼저 관리하고, 청킹 버전마다 대응 Chunk ID를 생성해 청킹 변경 시 평가 기준이 깨지지 않도록 한다. 튜닝용과 최종 확인용 문항을 구분한다.

- Hit@K: 정답 근거 중 하나 이상을 찾은 질문 비율
- Recall@K: 질문별 필요한 정답 근거 중 검색된 비율의 평균
- MRR: 첫 정답 근거 순위의 역수 평균
- 답변: 정답성, 관련성, 근거 충실성, 근거 없는 주장, 답변 불가 질문 처리
- 운영: 검색·Rerank·생성 지연, 전체 지연, 호출 수 및 가능한 경우 비용

답변 불가 문항은 Retrieval 지표 평균에 섞지 않고 별도로 평가한다. 검색 지표는 조문·항 또는 Chunk 중 어떤 단위를 썼는지 명시하고, 다중 근거 질문은 Recall을 함께 본다. 답변 평가 기준은 실험 전 고정하고 사람의 원문 대조를 포함한다.

최종 보고서는 단계마다 다음 순서로 작성한다.

1. 관찰한 문제와 실제 실패 질문·원문 예시
2. 원인 가설과 고려한 해결 방법
3. 선택 기준: 근거 보존, 검색 품질, 구현 시간, 지연, 비용
4. 적용한 변경과 고정한 실험 조건
5. 전후 수치 및 답변·출처 사례
6. 남은 실패와 다음 개선점

실험 기록에는 데이터 버전, 청킹 설정, 모델 설정, 검색 모드, 후보 수, 최종 K, 평가셋 버전, 코드 버전을 남긴다. 개선이 없거나 성능이 떨어진 결과도 보고한다.

## 8. 단계별 완료 기준과 충돌 방지

### 3시간 기본 일정과 1시간 추가 일정

| 경과 시간 | A: 본인 | B: Rerank·API | C: Multi Query·평가 | 공동 확인 |
|---|---|---|---|---|
| 0~15분 | PDF 구조 확인, 계약 합의 | 모델·Qdrant 연결 확인 | 계약 합의, 평가 형식 정의 | 모델 ID·임베딩 설정, 공통 함수 확정 |
| 15~30분 | 대표 조문 5~10개를 샘플로 공유, 전체 추출 진행 | Dense·API 골격, 샘플 연결 | 고정 후보로 병합 로직, 질의 확장 | 샘플 스키마 고정 |
| 30~75분 | 전체 청킹·원문 대조·적재 | Dense → Context → 답변 → /ask, Rerank 모듈 | Multi Query 모듈, Golden Set 초안, 지표 계산 | C는 B의 공통 Dense 함수에 연결 |
| 75~120분 | 전체 컬렉션 전달, 평가 정답 확인 | 전체 문서 MVP 확인, Rerank 연결 | Multi Query 연결, 동일 평가셋 실행 | 늦어도 120분에 Dense /ask 확보 |
| 120~150분 | 실패 조문·출처 검토, 노트북 정리 | 기준선·Rerank 평가, 오류 수정 | Multi Query 평가, 결과 표 정리 | 최소 세 모드 비교, 여유가 있으면 결합 모드 |
| 150~180분 | 데이터 문제·선정 기준 작성 | API 실행 설명·답변 사례 작성 | 지표·실패 사례 정리 | 재실행 확인, 제출물·보고서 초안 확보 |
| 추가 180~240분 | 청킹 실패 한 가지 개선 및 비교 | 결합 모드, 답변 품질 확인 | 평가셋 확장·결합 비교 | 한 번의 개선 전후 기록, 보고서 보완 |

75분 시점에 전체 적재가 늦으면 데이터 추출·조문 경계 문제 해결을 우선하고 검색 튜닝을 줄인다. 120분 시점에 MVP가 미완성이면 API 통합을 우선하며 결합 모드와 추가 청킹 실험을 후순위로 둔다. 문서 일부로만 실행되면 부분 처리임을 명시하고 전체 완료로 보고하지 않는다.

### 제출 최소선

전체 PDF에서 검증한 Chunk와 Qdrant 적재, 출처를 포함하는 /ask, Dense·Rerank·Multi Query의 작은 동일 평가셋 비교, 실행 가능한 단계별 노트북, 문제·선정 기준·실험 결과를 담은 보고서를 기본 목표로 한다. 결합 모드, 다수 파라미터 탐색, 배포는 추가 시간에 수행한다. 개선 효과가 없더라도 실제 결과와 실패 원인을 남긴다.

| 단계 | 완료 기준 |
|---|---|
| M0: 계약 합의 | 세 사람의 책임, 데이터 형식, 검색 인터페이스, 모델 환경 확정 |
| M1: 병렬 작업 시작 | 실제 소량 샘플 공유, Dense 공통 호출 가능, 두 검색 모듈과 평가 도구 작업 시작 |
| M2: 전체 MVP | 전체 문서 적재, Dense 기반 /ask, 답변과 원문 출처 연결 |
| M3: 검색 개선 | Dense·Rerank·Multi Query 실행 및 동일 Golden Set 비교, 시간 확보 시 결합 모드 추가 |
| M4: 제출 | 노트북 재현 절차, API 실행·요청 예시, 최종 보고서와 실패 사례 정리 |

디렉터리 소유권 제안: A는 ingestion/, B는 retrieval/dense.py, retrieval/rerank.py, api/, generation/, C는 retrieval/multi_query.py, evaluation/. 공통 schemas/는 초기에 합의하고 변경 시 먼저 공유한다. 기존 강사 코드가 확인되면 그 구조에 맞춰 조정한다.

공유 컬렉션을 각자 덮어쓰지 않는다. 재청킹 실험은 새 컬렉션·데이터 버전으로 분리한다. 공용 노트북을 동시에 수정하기보다 단계별 노트북을 나누고 제출 시 목차로 연결한다. 라이브러리 버전과 의존성 파일 변경은 통합 담당자가 모아 반영한다. API 키는 코드·노트북·보고서에 저장하지 않는다.

## 9. 논의가 필요한 정보

- 다른 두 팀원의 경험 및 실제 작업 가능 시간
- 강사 제공 코드 위치와 필수 기술·모델 조건
- MonoRouter API 호환 형식, 사용 가능한 모델 ID, 임베딩·Rerank 지원 여부와 비용 한도
- 제출 형태가 로컬 실행인지 배포까지 필요한지

총 3~4시간과 본인의 데이터·청킹 역할은 확정했다. 남은 정보가 확인되면 모델 호출 방식과 기존 코드에 맞춰 이 계획을 조정한다.
